**24. No refresh-token / silent-renewal flow in the frontend auth pattern**
Type: Known limitation (v1) · Source: ADR-0011 (carried forward unchanged by ADR-0012), `WI-WEB-001`/`WI-AUTH-005` · Hat: Engineering/Build, Architect
Status: Resolved 2026-11-02
Resolution: ADR-0019 and `WI-AUTH-007`. The login is a server-side session behind an HttpOnly cookie: the server holds the access and refresh tokens (encrypted, in Redis), renews the access token before it expires, and a reload keeps the login. The mock issuer gained the refresh-token grant. Shown in the browser tests of both apps (reload keeps the login, renewal, a refused renewal ends the session) and against the real mock issuer and a real Redis in the skeleton suite (see `docs/evidence/WI-AUTH-007/`). The text below is the original.
Access tokens are held in memory only and expire with no background refresh — a user simply gets logged out and must re-authenticate. Acceptable for a local/demo-scale app with short sessions; a real production frontend would need either silent-refresh-via-hidden-iframe or a refresh-token grant (the latter would also reopen the cookie-vs-header storage question closed in ADR-0006 §3.3's CSRF analysis, so isn't a drop-in addition). Named here explicitly rather than left as an unstated gap, consistent with `WI-NFR-001`'s "aspirational/future" discipline.

**29. Redis Streams consumer groups are named per event type, not per service**
Type: Tech debt / latent defect · Source: `WI-EVT-003` code, found by `WI-CAT-001` · Hat: Platform Engineering
Status: Resolved 2026-11-01
Resolution: `RedisStreamsEventTransport` takes an optional `serviceName`; with it the group is `cg:{serviceName}:{eventType}`, so two services each receive every message and instances of one service share the work. The catalog passes `catalog-service` (its vendor-status subscription starts a new group and replays the stream's history, which is safe because it dedupes by sequence number; the old `cg:` groups stay in Redis unused). Ordering will pass `ordering-service` when it subscribes (`N-03`). Without a name the old per-event-type group is kept, so a caller that forgets to pass one is not protected. Shown against the local Redis (3 tests in `RedisStreamDeliveryTests`; they skip unless `REDIS_CONNECTION_STRING` is set).
Original text: `RedisStreamsEventTransport` uses group `cg:{eventType}`. Two services subscribing to the same event would compete for messages instead of each receiving all of them. Harmless while a single service consumes each event; fix before `ordering-service` or `notification-service` subscribes to a shared one (group name should include the service).

**76. A vendor's order lookup fans out across every customer's partition, and there is no "my orders" list**
Type: Known limitation · Source: `WI-ORD-007` (2026-10-28) · Hat: Architect, Engineering/Build
Status: Resolved 2026-11-01 (ordering service; the BFF schema and a vendor UI are not part of it)
Orders are partitioned by customer (ADR-0004), but a vendor acting on an order knows only the order id. Orders that confirmed themselves (`WI-ORD-008`) never reach the vendor as a decision, so the vendor has no way to see them either until this read side exists (the `Automatic` flag on `OrderConfirmed` is there for it). `OrderStore.GetForVendorAsync` therefore queries `id` and `vendorId` across all partitions on every vendor action. That costs more request units as orders grow, and it is on a request path (the empty partition key was meant for background work). Options when it matters: a vendor-keyed read model fed by the order events (the `QUE-001` direction), a second container or lookup document partitioned by vendor, or having the vendor client pass the customer id. The same read model would give vendors the "my orders" list that does not exist yet; nothing shows a vendor which orders are waiting. Not measured against real Cosmos.
Resolution: a vendor order read model (`N-03`). The `vendor-orders` Cosmos container, partitioned by `/vendorId`, holds one `VendorOrderDocument` per order (status, totals, pickup window, who cancelled and why, the customer id for the lookup). `VendorOrderProjection` applies the six order events, subscribed in the ordering service under its own consumer group (`VendorOrderSubscriptions`); it is idempotent and tolerates out-of-order and repeated events (the status follows the highest event sequence, facts are only ever filled in). `GET /ordering/vendor/orders?status=&limit=&after=` (Vendor role, the vendor id from the token) lists a vendor's orders newest change first, `status` being `active`, an order status, or absent for all; the customer is not shown. `OrderStore.GetForVendorAsync` now reads the read model and then the order by customer id (two point reads), and falls back to the old cross-partition query when the read model does not have the order yet. To make this possible the order lifecycle event payloads gained optional `VendorId` and `CustomerId` (additive; older messages still read, and an event with no vendor id for an unknown order is skipped with a warning). **Added 2026-11-01 (the vendor needs to decide without a second read):** `OrderPlaced` now also carries the requested fulfillment type and details (the window and instructions; additive, absent when no window was requested), the read model keeps the lines (listing id, modifier ids, quantity) and the instructions, the list items show them, and `GET /ordering/vendor/orders/{id}` is a point read of one order in the vendor's own partition (404 for another vendor's, an unknown, or a not-yet-projected order). **81. A retry under the key of a rejected checkout gets `conflict`, not the original answer**
Type: Rough edge · Source: `S1-07b` (2026-10-28) · Hat: Engineering/Build
Status: Open

**113. The vendor order view needs names, and must say what still costs a read per order**

**118. Sessions live in an LRU cache Redis, so a full cache ends logins**

Status: Approved 2026-11-06, not built · a separate `redis-sessions` instance with `noeviction` (eviction policy is per instance, so a key prefix or numbered database in the cache Redis cannot be protected from `allkeys-lru`) in `docker-compose.yml` and the dev Terraform

**125. A hung Redis can hold up every stream open or close on an ordering instance**
Type: Hardening · Source: security review of `WI-QUE-003`, 2026-11-02 · Hat: Platform Engineering
Status: Resolved 2026-11-02
Resolution: `VendorOrderStreamHub` keeps one lock per vendor (a `SemaphoreSlim` in each vendor's entry) and counts the instance's streams with an atomic reserve-and-release instead of under a lock, so a slow Redis subscribe delays only that vendor's own opens and closes; the guarantees of the single lock are kept (one subscription per vendor, the limits, no stream left on a subscription being disposed). Tests in `VendorOrderStreamHubTests.cs`: a stuck subscribe for one vendor does not delay another vendor's open or close (fails on the old hub), 40 opens at once for one vendor leave the limit, one subscription and an exact count, 60 opens at once never pass the instance limit and give back the places they were refused, 200 rounds of a close racing an open never leave the new stream on a disposed subscription, and a failed subscribe leaves nothing behind. Approved by the lead the same day.
`VendorOrderStreamHub.OpenAsync` and `ReleaseAsync` take one gate, and `OpenAsync` waits for the Redis subscription inside it (`RedisBroadcast.SubscribeAsync`, which has no timeout of its own beyond the client library's default of about 5 seconds). With Redis unreachable that is quick to fail and the endpoint answers 503, but with Redis slow or half-open every other vendor's open, and every close, queues behind it for that time. Fix: subscribe outside the gate (create the vendor's entry first, with the subscription as a task the later openers await), or give the subscribe its own short timeout; with a test that a slow subscribe for one vendor does not delay another's.
What the lock is for (asked at the review, 2026-11-02): `_gate` in `VendorOrderStreamHub` is the one lock of the hub's bookkeeping. It makes four things atomic that must not interleave: finding or creating a vendor's single broadcast subscription on this instance; counting streams against the per-vendor (5) and per-instance (500) limits and retiring the oldest; adding or removing a stream from the vendor's list; and unsubscribing when the last stream goes, so that a stream opening at that moment cannot end up with a subscription that is being disposed. It is correct; the problem is only that the Redis subscribe, a network call, runs while it is held. The fix keeps the guarantees with a lock per vendor instead of one for all, and the subscribe awaited inside only that vendor's lock.

**137. The BFF's rate-limit backstop is counted per source address, which is the web app's server, so it is shared by every user of that web app**
Type: Design weakness · Source: the first trial of the load script, 2026-11-02 (`docs/evidence/WI-SEC-005/load-soak-2026-11-03.md`) · Hat: Security, Architect
Status: Decided 2026-11-06, not built · the lead chose option B: the web app passes the client's address in a header, the BFF trusts that header only from the web app's own address (a trusted-source setting, like `TRUSTED_PROXY_HOPS`), and counts per client. Callers that are not the trusted source (the Android app, direct calls) are still counted by their own address. Rate-limit trust logic is security-adjacent: the build needs the lead's approval of the design before code, tests that show a spoofed header from an untrusted source is ignored (and fail with the check removed), and an update of `WI-RATE-001`. To be scheduled as a work item.
`WI-RATE-001` gave the BFF a coarse ceiling of 600 requests a minute per source address. In practice the only source is the web app's server, so the ceiling is on the whole web app, not on a user. The web apps limit each address (600 a minute) and each login (120 a minute), so one client is held well below the BFF's ceiling; but a number of clients from different addresses, or one client with many logins, can together exceed 600 a minute and then every user of that web app is refused until the window passes: the backstop protects the BFF by turning overload into an outage for everyone, not by shedding the abusive caller. The load script's first trial showed it (two readers in a loop used the whole allowance and customers' orders were refused with a rate-limit error). "Reconciled" means choosing one of: raise the ceiling to a multiple of the expected peak and accept that it is a safety net only; make the web app pass the client's address to the BFF in a header the BFF trusts only from the web app's own address (a trusted-source setting, as `TRUSTED_PROXY_HOPS` does for the web app) and count per client; or drop the BFF's counter and rely on the web app's per-login and per-address limits. The numbers in `WI-RATE-001` were the lead's starting values.
