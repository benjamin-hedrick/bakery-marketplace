## What the session did

The vendor read side (the order read model, the cached listing names, the vendor order endpoints and the BFF queries), the vendor's live order queue screen (`WI-QUE-002`), a fix for a catalog test deadlock on few cores (register item 117), ADR-0021 (push for the queue) and ADR-0019 (browser sessions) drafted and accepted, `WI-AUTH-007` phases 1 to 4 (the mock issuer's refresh grant, the shared `packages/web-session`, both web apps moved onto it, the real-stack runs recorded in `docs/evidence/WI-AUTH-007/`), a first-pass security review, and register items 113 to 122.

## How to read the numbers

- **This session cost about twelve times session B (relative cost 1.44) and about three and a half times session A (relative cost 4.79)**, because it was far larger: about 7 times the output tokens of session B and 2.4 times those of session A, and a compaction in the middle. The cost follows output tokens and cache writes, not the lines-added figure.
- **Cache reads dominate the token counts** because each request resends the whole conversation from the prompt cache; the 218.6M figure does not drive the cost.
- **Lines added is not a quality or productivity measure.** It counts documentation, tests, generated lock files and the evidence records as well as code.
- **No claim is made about value per unit of cost.** One session is not a sample, and the human review time is not in these figures.

## What this does not show

The human review, decisions and approvals in the session (the lead made the choices recorded in ADR-0019 and ADR-0021 and approved the auth changes); which problems the lead caught that the model had not; the security review's independence (the first pass was the model reading its own session's code); and any session other than this one.
