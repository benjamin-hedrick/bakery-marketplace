## What the session did

The lead ran the first full dev deploy after `feature/dev-app-deploy` was merged. The plan stage planned 27 to create; the apply step then stopped with exit 1 and no message, straight after the foundation `init`. Nothing was created.

- **Narrowed from the log:** the one `init` in the failed step installed only the foundation stack's provider, so the step stopped between the foundation's outputs and the dev stack's `init`, where `jq -e` lookups exit 1 without a word on a missing value. The foundation's outputs were read from the lead's sign-in (names only) and were complete.
- **Likely cause:** the shared setup script read the environment from the `ENVIRONMENT_NAME` environment variable, which a deployment job sets to its own environment name (`dev-infra`). The old script run in Ubuntu with that value reproduced the log exactly. Why attempt 3's apply and the first teardown passed with the same code is not explained (register 201 (30)).
- **Fixed:** the environment is passed as an argument by the pipeline's macro, and each foundation lookup names what it could not find. Checked with the pipeline-structure tests (one new), the script run in a container with a stubbed Terraform, the Node gates and the secret scan. Pushed for the lead's pull request; **not yet run in Azure**.

## Errors the assistant made, and what caught them

Register 201, (30): the script read a variable name the platform also sets, and its lookups failed silently (caught by the lead's pipeline run; one run lost, nothing created). Smaller, caught before the commit: the first lookup message went to stdout inside a command substitution, where the log would not show it (caught on review); a test harness ran the script inside an `&&` list, where bash ignores `set -e` (caught by its own output); the new test's formatting (caught by the Node gates).
