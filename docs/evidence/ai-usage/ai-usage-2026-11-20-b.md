## What the session did

The second half of the lead's goal 2 (deploy dev with evidence), built and run locally where it can be, **not yet run in Azure**. Everything is on `feature/dev-app-deploy`, one pull request for the lead.

- **Images:** the six images the dev stack runs are built with no service connection beside the plan, and pushed by the deploy identity only after the application approval, refused unless they are the images the build recorded (the lead chose build first, push after approval). Run locally: built, pushed to a throwaway local registry, a tampered id refused.
- **Secrets:** the post-apply step sets each Key Vault secret that still holds its placeholder, each value only through a mode-600 file in the job's temporary folder, deleted at once, to the rules decided before it was built; a redeploy rotates nothing.
- **App update:** each app to its pushed digest in a new revision, refused if any app runs a newer build (register 110); register 217 records that an apply is expected to put back the placeholder image.
- **Seed:** the seed may write to the deployed dev environment behind a named switch (register 224, approved by the lead), and runs as a job inside the environment, before the apps update; a new seed listing for the concurrency test.
- **Smoke and observe:** a stage with no credentials runs an 11-test customer suite through the public addresses (including five customers ordering the last two units at once) and a latency run; a read-only stage reads metrics, log counts and which correlation ids reached the log. Dry run on the local stack: 9 passed, 2 failed by design (they need https), the concurrency test passed (2 of 5 orders confirmed, 3 refused for stock).
- **A defect found before any run:** behind the ingress the mock issuer would have advertised http addresses the services refuse (register 226); seen locally with a forwarded request, fixed with the lead's approval.
- **Recorded for later** (registers 218 to 225): what dev does not test that local does, vendor logins and the vendor app, the Android app and the public BFF, observability, Entra not specified, plain http inside the environment, a local tooling defect.

## Errors the assistant made, and what caught them

Register 201, (27) to (29). The traceability table was stale on the previous session's pushed commit (caught by this session's first gate run, before any push). A register edit script was written through a heredoc against the repository's rules (caught when reviewing the step). The deployed suite's first dry run used anchored selectors and no action timeout, so three tests waited out their timeout (caught by the dry run itself). Smaller ones, caught by the tests before anything was committed: a fixture digest of the wrong length, a pipeline test that matched rehearsal text, a test count that ignored comment lines, and an image publish that failed on duplicate settings files (caught by building the image).

## How to read the numbers

- **Relative cost is a size, not a price.** 13.19 is one of the larger sessions: four pipeline steps, a job, a suite of browser tests and three evidence scripts, each with tests, two local stack runs and two image builds, and the lead's design decisions between them.
- **Much of the elapsed time was local runs** (the skeleton smoke, the dry runs, the Linux check) and the lead's answers; the screen's API time counts the assistant only.
- **No claim is made about value per unit of cost.** The human review time is not in these figures.
