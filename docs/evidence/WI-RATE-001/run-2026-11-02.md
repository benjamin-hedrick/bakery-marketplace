## What the first run found

The first run of the queue display's mock-backed suite with the default limits **failed 3 of 32 tests and took 2.6 minutes**: the suite logs in many times a minute from one address and was refused. The browser suites therefore set the web limits out of the way (`RATE_LIMIT_*` in the two Playwright configs), and the limits are tested on a second server with tight settings. A person does not log in that fast; a test suite does. Anything else that logs in repeatedly from one address (a demo script, a load test) has the same effect and must set the variables (`docs/operations/local-dev.md`).

## Tests shown to fail with the behavior removed

Each was taken out in turn and the package or BFF tests failed, then it was put back: the login limiter, the stream-open limiter, the bound on the number of keys, the use of the proxy hop count (the client is the entry the trusted proxy added, not the first entry), the order of the address check before the session lookup (the junk-cookie flood then reached the session store), and the BFF refusal; each made at least one test fail. Two things could not be mutated: the explicit "0 hops means ignore `X-Forwarded-For`" guard (the code gives the same result without it, because there is then no entry that many places from the right, so the test still checks the behavior but not the guard), and the browser tests of the tight server, which run against the built app and were not run against a build with a limit removed.

## What this does not show

- Behavior under load: no test approaches the limits at speed or for long (register item 129).
- Any proxy: `TRUSTED_PROXY_HOPS` was tested with a header the test sets, not with a real ingress.
- More than one replica: the counts are per process.
- Containers mode, Azure, a real identity provider.
- The limits were chosen by the lead as starting values; they are not derived from measured use.
