## What the session did

All seven steps of `WI-QUE-003` (live updates to the vendor's order queue, ADR-0021) and the review that followed: the broadcast adapter with its contract tests, ordering's stream endpoint (the vendor from the token, the end at the token's expiry, limits, a write timeout), the Redis fan-out across two hosts, the `graphql-sse` dependency review (including rebuilding its source tag and comparing every file), the BFF subscription, the web app's streaming route, the queue display's Live and Polling modes, exported stream metrics, the real-stack runs with the measured delay (host processes and containers), a first-pass security review, and the fixes the lead asked for at the review (a limit and back-off on the session check, a write timeout, a lock per vendor, places counted after the request is read and a limit per login). It also fixed the JSON route's missing body limit (register item 124), corrected an out-of-date NFR (section 3.3, CSRF), recorded register items 123 to 131 (among them the session hand-off, rate limiting, load and fuzz and penetration testing, and the process review), and corrected the plan and memory at the start of the session.

## How to read the numbers

- **This session cost about 60% of session C (17.41), about 2.2 times session A (4.79) and about 7 times session B (1.44).** Its output was 417.8k tokens against 613.5k for session C, 252.6k for A and 89.5k for B, and it had no compaction. The cost follows output tokens and cache writes, not the lines-added figure.
- **Cache reads dominate the token counts** because each request resends the whole conversation from the prompt cache; the 122.3M figure does not drive the cost.
- **Lines added is not a quality or productivity measure.** It counts tests, documentation, generated lock files and the evidence records as well as code.
- **No claim is made about value per unit of cost.** One session is not a sample, and the human review time is not in these figures.

## What this does not show

The human review, decisions and approvals in the session (the lead chose the dependency version, approved each security-sensitive step, asked the questions at the review that led to five of the fixes, and approved the item as Done on conditions); which problems the lead caught that the model had not (the first-pass review and the lead's questions found different things, and both are recorded in the work item); the security review's independence (the first pass was the model reading its own code, which is why register item 129 asks for a plain statement of what has not been independently reviewed); and any session other than this one.
