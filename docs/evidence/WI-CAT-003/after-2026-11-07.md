# WI-CAT-003 latency with and without the listing cache

> **Status:** Snapshot · 2026-11-07

**Current result:** passed. With the listing cache on, the BFF listings query went from about 20 ms to about 3 ms at p50 and the server-rendered home page from about 24 ms to about 8 ms, on the seeded catalog. Checkout and the pickup-windows read did not change beyond the run-to-run spread. Three runs each, one machine.

- **Commit:** `6a384d8` on `feature/listing-cache` (the cache code is the same in both modes; the only difference is the setting).
- **Cache off:** `ListingCache__TtlSeconds=0 node scripts/dev/demo.mjs --stop-after 170`, then `node scripts/dev/measure-latency.mjs --reads 50 --orders 20` three times. **Cache on:** the same without the setting (the default, 60 seconds, the in-process provider).
- **Comparison with the earlier baseline:** `baseline-2026-11-07.md` (one run, before the cache code existed) is in the same range as the cache-off runs below.
- **Method:** sequential requests, one at a time: latency, not capacity. Percentiles are nearest-rank. One Windows machine; host processes for the services, Docker for Redis, the Cosmos emulator and the mock issuer.
- **Limits:** the seeded catalog is small (7 listings, 2 verified vendors), so these are the numbers for a small catalog; a larger one would show more of the saving. The in-process provider only: the Redis provider adds a network hop per read and was not measured here. Three runs each is a small sample; the two groups do not overlap on the browse rows.

| Request (p50 ms, three runs) | Cache off | Cache on |
|---|---|---|
| browse: BFF listings query | 26.4 / 18.9 / 19.9 | 2.6 / 3.1 / 3.5 |
| browse: home page (server-rendered) | 32.5 / 24.1 / 23.8 | 8.2 / 8.3 / 10.1 |
| read: BFF pickup windows | 3.8 / 2.4 / 2.3 | 3.0 / 3.1 / 3.4 |
| checkout: later orders | 74.4 / 65.3 / 59.9 | 58.5 / 60.1 / 47.1 |

| Request (p95 ms, three runs) | Cache off | Cache on |
|---|---|---|
| browse: BFF listings query | 35.1 / 29.5 / 25.1 | 4.4 / 4.5 / 6.5 |
| browse: home page (server-rendered) | 41.2 / 32.1 / 31.5 | 11.4 / 12.9 / 16.9 |

No request failed in any run.

**The slow first checkout.** The first checkout after a stack start took about 2.5 s in the first run of each mode (2598.6 ms off, 2461.5 ms on) and 55 to 66 ms in the other four runs. It is a start-up cost (first connections and compilation), the same with the cache on or off, so the cache did not cause it and does not fix it.

**What this does not show:** invalidation correctness (the unit and integration tests do: `ListingCacheTests`, `ListingCacheConfigTests`, `ListingCacheRedisTests`), staleness under several replicas, or behaviour with the cache Redis in use.
