# Latency measurement (2026-10-30)

> **Status:** Snapshot · 2026-10-30, `scripts/dev/measure-latency.mjs` against the demo stack (`scripts/dev/demo.mjs`), Windows 11, Docker Desktop, Node 25.9.0, .NET SDK 10.0.401 (`WI-QA-002`, rows `T-27` and `G-H08`). **Current result:** on a warm stack, reads answer in tens of milliseconds (p95 33 to 42 ms for the BFF listings query, 42 ms for the server-rendered home page) and a checkout in about 63 ms (p95 75 ms); the first checkout after the stack starts took 4.6 s. No latency target exists to compare with (`nfrs.md`), so the question of whether the design meets its targets cannot be answered; the numbers are a measured starting point (register item 100).

## Method

One stack, started once, then the script run twice in a row. Requests are sequential, one at a time, from the same machine to the BFF (`:4100`) and the web server (`:3000`); every part runs on that machine, so no network is included. Per run: 50 rounds of three read requests, then 20 test orders (one Country Sourdough each, as Alice Customer, a new idempotency key each); the vendor first adds stock so the orders do not sell the listing out. Percentiles are nearest-rank. This measures latency, not throughput or capacity.

## Results

First run, on a stack that had just started (the demo's warm-up had read the issuer metadata, the home page and the pickup times; no order had been placed):

| Request | n | Failed | p50 ms | p95 ms | max ms |
|---|---:|---:|---:|---:|---:|
| browse: BFF listings query | 50 | 0 | 33.2 | 41.6 | 44.8 |
| browse: home page (server-rendered) | 50 | 0 | 42.2 | 54.5 | 57.3 |
| read: BFF pickup windows | 50 | 0 | 4.9 | 8.5 | 13.6 |
| checkout: first order of the run | 1 | 0 | 4602.2 | 4602.2 | 4602.2 |
| checkout: later orders | 19 | 0 | 69.1 | 79.7 | 79.7 |

Second run, immediately after, on the now-warm stack:

| Request | n | Failed | p50 ms | p95 ms | max ms |
|---|---:|---:|---:|---:|---:|
| browse: BFF listings query | 50 | 0 | 26.1 | 33.3 | 38.7 |
| browse: home page (server-rendered) | 50 | 0 | 32.4 | 42.0 | 47.1 |
| read: BFF pickup windows | 50 | 0 | 3.6 | 5.2 | 8.5 |
| checkout: first order of the run | 1 | 0 | 69.5 | 69.5 | 69.5 |
| checkout: later orders | 19 | 0 | 63.4 | 75.3 | 75.3 |

## Reading it

- The cold cost is per stack start, not per script run: the first order took 4.6 s once and 69.5 ms in the second run. This matches the 4.7 s of `docs/evidence/slice-1/findings.md` and explains why the demo's warm-up (reads only) does not remove the slow first checkout (register item 98). The 7 s seen in a browser (`docs/operations/demo.md`) was timed from the click on "Place test order" to the order page, so it includes the browser's own work as well as the call; that split was not measured.
- The slower first read run against the second (33 ms against 26 ms at p50) fits warm-up as well; whether the stack was fully steady by then was not checked.
- Warm checkouts are 63 to 69 ms at p50 through the BFF, ordering and the catalog, consistent with the 55 to 78 ms of the earlier baseline.
- Not measured: concurrency, throughput, a deployed network, the browser (rendering, hydration), the Cosmos emulator under load, and anything beyond 70 requests per type. One machine, one run each way: variation between machines or days is unknown.
- `G-H08` (the BFF and cache design meet the NFR targets): there is no latency target and no service uses the cache, so the claim has nothing to be tested against. Setting a budget is a decision for the lead; the numbers above are the data for it.
