# WI-SEC-005 step 4: OWASP ZAP scan of the local stack, 2026-11-03

> **Status:** Done for the local stack · run by the AI agent on a developer machine (Windows 11, Docker Desktop, ZAP from `ghcr.io/zaproxy/zaproxy:stable`). Command: `node scripts/ci/zap-scan.mjs` (it starts the stack, builds both web apps, scans, and tears down). Two runs: the first on commit `8ad50ec`, the second on the working tree that became the commit holding this record, after the fixes below. Reports: `zap-first-scan/` and `zap-second-scan/` in this folder (markdown reports and the summaries).

## What was scanned, and how

| Target | Scan | What it does |
|---|---|---|
| Customer app, `http://localhost:3000` | ZAP baseline (`zap-baseline.py`, 1 minute of spidering) | spiders the pages and applies the passive rules to what it sees: headers, cookies, information leaks. No attack requests. |
| Queue display, `http://localhost:3100` | the same | the same |
| GraphQL BFF, `http://localhost:4100/graphql` | ZAP API scan (`zap-api-scan.py -f graphql`) | imports the schema by introspection and sends attack requests (the active rules) at every operation |

The scan is **unauthenticated**. It sees what an anonymous visitor sees: the public pages, the login redirect, and the BFF's public queries. It does not see the pages behind a login (the queue, the order pages), the session cookie after login, or the vendor actions, because no login script for ZAP exists.

## What was done about each

- **`script-src 'unsafe-inline'` (Medium):** known and documented (register item 134, threat model E4). Next.js writes inline scripts with no fixed hash; moving to nonces needs a middleware and dynamic rendering of every page. Not fixed.
- **`style-src 'unsafe-inline'` (Medium):** not previously listed; the apps and Next.js use inline styles. Not fixed; the risk is lower than for scripts.
- **`X-Powered-By` (Low):** fixed (`poweredByHeader: false` in both apps).
- **Cross-Origin Opener Policy and Resource Policy (Low):** fixed (`same-origin` on every response of both apps; the BFF sends the resource policy).
- **`X-Content-Type-Options` missing on the BFF (Low):** fixed (`nosniff` on every BFF response, errors included).
- **Cross-Origin Embedder Policy (Low):** not set. It is for pages that embed cross-origin content and need cross-origin isolation; neither app does.
- **Informational items:** read, no action. The 17 client errors are the API scan's own malformed and hostile requests being refused (400s), which is the expected answer.

The fixes have tests (`security-headers.spec.ts` in both apps; `test/limits.test.ts` for the BFF), and both mock-backed browser suites pass with them (queue display 53, customer 68).

## What this does not show

- Anything behind a login (the vendor's queue, the actions, the order pages, the session cookie as set after login), and role-specific behavior.
- The .NET services directly (catalog and ordering were reached only through the BFF).
- A scan on a deployed system, over HTTPS, behind API Management, or with a real identity provider.
- That the default ZAP rules find what a person would. A baseline scan is passive; the API scan attacked the GraphQL layer only. It is not a penetration test.
- Whether the API scan's attack requests exercised the BFF's new size limits in ways that matter (it reported nothing about them).
