## What it found

1. **A request that ended the BFF process** (register item 136). `{"query":"{ __typename }","variables":"x"}`, no token needed. The first run of the route fuzz did not finish: one request got no answer within 5 seconds; reproduced on a standalone process, which exited. Fixed in the same step (validation of `variables` and `operationName`, a catch around the execution) with a test that starts the real process and fails without the fix. The web apps send request bodies on unchanged (a reading of the proxy, not run end to end), so the request should have been possible from a browser without a login.
2. **A variable that could not be coerced was reported as `INTERNAL`** and logged as a failed resolver (342 of the first 1,200 generated requests). Fixed: such an error has no path and is returned as the caller's mistake.
3. **No limit on the cost of an operation** (register item 135, already registered from the threat model): one request of 62,649 bytes with 1,328 aliases made the BFF open 57 downstream calls, 56 of them at once, before failing with a generic error. This is recorded as a measurement; nothing limits it yet.

The package's generated-input tests found nothing, and each of the properties was shown able to fail: removing the control-character rule from `safeReturnTo` failed the test at case 12, and removing the `//` rule failed it at case 110.

## What this does not show

- Coverage-guided fuzzing (no corpus, no instrumentation), a longer run, or fuzzing of the .NET services' inputs.
- The web apps' route handlers under a generated HTTP load (the properties are on the functions they use).
- The GraphQL schema's resolvers with a real catalog or ordering behind them: the stubs answer with valid bodies. A downstream that sends hostile bodies is the stream reader's case only.
- The cost of the alias request on the real services.
