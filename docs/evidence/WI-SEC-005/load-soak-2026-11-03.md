## What ran

1. **The stream limit.** One vendor opened seven streams one after another. Ordering keeps five per vendor and ends the oldest when a sixth opens.
2. **The load.** Five vendor streams stayed open for 65 minutes. A customer placed one order every 5 seconds (with an option, so each waited for the vendor). Two readers looped over the listings and pickup-window queries with a 200 ms pause (about 16 requests a second in all).
3. **A restart.** At the midpoint the ordering service was stopped and started again (requested outage 10 seconds; it was 19 seconds before ordering answered its health check).
4. **Memory.** The working set of the three processes was sampled every 30 seconds.
5. A stream reopens with a fresh token when it ends, and after each reopen reads the list so nothing that happened while it was away is missed, as the real screen does.

## How to read this

- **The run passed:** the limit held, nothing was missed, nothing failed outside the outage, memory did not grow. Exit code 0.
- **My own test runs disturbed part of it.** Between about 03:10 and 03:40Z I ran browser and unit suites on the same machine while the soak was running, so the latency figures include that contention. The p99 and the 1,510 ms maximum may come from then; the report does not say when each sample was taken, so I cannot separate them. The p50 and p95 are the better figures and are likely to be the same or lower on a quiet machine.
- **The token's hour.** The run lasted 66 minutes, longer than the mock issuer's one-hour tokens, and screens fetch a fresh token each time they reopen. Each screen opened 7 times; the report does not separate a reopen at token expiry from the reopens after the restart, so this run does not on its own prove the renewal at expiry. Nothing was missed across the whole 66 minutes.
- **The failures during the outage are generic by design** (the client sees "Something went wrong"). That is correct for an unexpected dependency failure, but a customer placing an order while ordering is down gets no more specific message.
- **Light by design.** One order every 5 seconds is far above the planning figure (200 orders a day) and far below a busy bakery's peak; five streams are the most one vendor may hold. This was not a test of the 500-stream limits (the seeded users allow three vendors, so at most 15 streams can be opened by real logins), of many vendors, of the web apps in the path, or of the real services under a proper database.

## What the first trial found

An earlier 2-minute trial placed 3 orders in 2 minutes and had 37 order errors: the BFF's own backstop (`WI-RATE-001`, 600 requests a minute per source address) refused them, because the readers alone made far more than that. This is the backstop doing what it was built to do, and it also shows a weakness, registered as item 137: the BFF sees only the web app's address, so one abusive client that gets past the web app's per-address and per-login limits can use up the allowance for every user of that web app. The soak sets the backstop out of the way so it measures the system, not the limit.

## What this does not show

The 500-stream and 500-per-BFF limits; more than three vendors; the web apps' routes under load; a real database or a deployed network; a browser's behavior (the stream client here is not the real screen); the renewal at token expiry on its own; the cost of a screen that reconnects together with many others after a restart (5 screens reconnected together here).
