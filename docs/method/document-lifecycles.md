# Document kinds and their lifecycles

> **Status:** Draft · started 2026-10-30, extended as each clean-up step defined or confirmed a kind; the clean-up is finished and the file was not finalised. Four rows are still marked *to confirm*: they have not been reviewed. Treat the rest as the working classification, not as a settled rule.

Every kind of document in the repository, how it is born, how its status is kept, and how it ends. The point is that a reader (or an agent) can tell which documents to trust for what, and which to leave alone.

## The rules that apply to every kind

- One source of status per kind of thing: the spec banner for work items, the status line for ADRs, the `Status:` line for register items, the banner for documents. Anything else is generated from those or is a pointer.
- History is changed by adding dated notes or new records, not by rewriting. Specs are the exception on purpose: a spec should describe what is true now, and git keeps the original.
- A claim that something works links to the run or says "not run".
- Numbers quoted in prose come from the facts sheet or the status table, not from memory.
