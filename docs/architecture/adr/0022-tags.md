# ADR-0022: Tags (a catalog-owned registry of kinds and tags, assigned to listings and options)

**Status:** Accepted (2026-11-04, approved by the lead; drafted the same day as Proposed). Drafted from the lead's decisions of the same day: the registry is versioned data first and an admin-edited store later; allergens belong to the same registry but keep their own listing fields for now; vendors assign tags to their listings and options; this record is wanted before the work items. It builds on ADR-0004 (Cosmos), ADR-0009 (catalog hosts the context), ADR-0013 (the BFF) and ADR-0014 (cache layers). It does not change any of them.

## Context

A listing today carries `allergenFlags` and each option carries `allergens`: free text, trimmed and lower-cased by the catalog. Nothing else describes a listing but its name, description and category. Three needs arrive together:

- **Personalization and safety.** A customer lists the allergens they must avoid; browse, the detail page, the cart and the order must be able to say "this contains it". Free text cannot do that reliably: the seed data says `tree-nut`, a customer will type "tree nuts", and the match fails silently, which in a safety feature reads as "fine".
- **Discovery.** Dietary preference (vegan, vegetarian, gluten-free), holidays, themes and seasons: context that supports search, filters, display and collections.
- **Behind the scenes.** Some context is for the platform, not the customer (ranking, moderation, merchandising), and some should be visible only for a time (a holiday window).

These look alike ("a label on an item") but are not the same kind of statement. "Contains sesame" is a warning, where silence means *unknown*, never *safe*. "Vegan" is a claim by the vendor, where silence means *not marked*. "Thanksgiving" is description, where silence means nothing. If one mechanism treated them alike, the code would either under-protect allergens or over-promise on the rest.

What the existing design already gives: the public listing endpoints are anonymous and cacheable (ADR-0014), the catalog owns listing data (ADR-0009, ADR-0017), vendors manage listings through the catalog API (the vendor admin app is not built), and services reach each other with the caller's token or a service token (ADR-0006, ADR-0018).

## Decision

1. **A tag registry, owned by the catalog.** Each entry has: a stable `id` (a slug: lower case letters, digits and hyphens, at most 40 characters, unique across all kinds, never renamed or reused; a retired tag is marked retired, not deleted), a `kind`, a display `label`, a `visibility` (`public` or `hidden`), `assignableBy` (`vendor` or `platform`), optional `activeFrom` and `activeTo` (UTC dates), and an optional sort order. Ids are the contract between services, the BFF and the browser; labels are for display and may change.
2. **The registry is versioned data now.** It is a data file in the catalog service, reviewed in pull requests like code, loaded at start and read through an interface (`ITagRegistry`), so a store with administrator editing can replace it later without changing any caller. It is served by a public, cacheable `GET /catalog/tags` (public tags only; see 6). No new Cosmos container.
3. **Kinds are a closed set defined in code, and a kind carries the semantics.** The first kinds are `allergen` (the listing contains it; absence means unknown), `diet` (the vendor says it suits that diet; absence means not marked), and the descriptive kinds `occasion`, `season` and `theme`. A kind decides the wording the product may use, how a listing's tags and its chosen options' tags combine, whether the tag may appear in a customer's profile, and whether it is recorded on an order. Adding a kind is a change to this record (an amendment), because it adds a meaning. Adding a tag to an existing kind is a data change.
4. **Attachment: listings and options.** Allergens stay where they are, `allergenFlags` on the listing and `allergens` on each option, with the same shape; their values are now validated against the registry (kind `allergen`) as a closed list, and an unknown value is a 422. They stay separate because they are safety-critical, already option-level and used by the order path. Every other kind goes in a new `tags` list on the listing and a new `tags` list on each option, with caps (proposed: 12 on a listing, 6 on an option). Folding allergens into `tags` can be revisited later; nothing here prevents it.
5. **Combining a listing's tags with its chosen options' tags is decided per kind.** `allergen`: the union (an option adds to the item, as now). Descriptive kinds: the union, for display. `diet`: not decided here. Diet tags on options are display-only until the work that matches diets decides the rule (the open question is how an option contradicts a claim: oat milk keeps an item vegan, whole milk does not). The matching phase records its rule as an amendment.
6. **Visibility is enforced by the catalog, never by the screen.** A `hidden` tag, and a tag outside its active window, is left out of every public response: listings, options, the registry endpoint and the BFF schema. Filtering and search treat it the same way. The catalog evaluates windows with its own time source at response time; the assignment stays on the listing, so a seasonal tag returns next year without anyone touching the listing. A cached public response can show or hide a tag for up to its cache lifetime after a window edge; that is accepted (ADR-0014).
7. **Assignment.** A vendor assigns tags with `assignableBy: vendor` to their own listings and options through the listing API (and later the vendor admin app); the catalog rejects any other tag. Tags with `assignableBy: platform` are stored apart from the vendor's, so a vendor update never sets or clears them. Hidden tags are platform-only. Platform assignment needs the administrator console (not built); until then it is seed data or an operator's change.
8. **Claims are the assigner's, and the wording says so.** The platform does not verify a vendor's flags or diet claims. The product says "marked vegan by the bakery" and "contains X, which you listed", and never "safe" or "free of X". A moderation or verification step is a future use (below), not a promise made now.
9. **Other contexts refer to tags by id and do not copy the list.** A customer's profile holds allergen ids (and, in a later phase, diet ids), matched by the catalog in a customer-only endpoint kept separate from the public browse. A service that must validate ids, such as ordering for allergens recorded on an order, reads the registry from the catalog and caches it; the mechanism is part of that work item.

## Options considered

| Option | Verdict |
|---|---|
| Free-text tags with normalization | Rejected: a match on free text can fail silently, and normalization only narrows the gap |
| One undifferentiated tag type | Rejected: it cannot tell a warning from a claim from a description, and the wording and the safety rules differ |
| Fold allergens into `tags` now | Deferred: the order path, option level and tests all use the existing fields; the registry gives the closed list without moving them |
| Registry in Cosmos with administrator editing now | Deferred: the administrator service and console are not built; the interface leaves the way open |
| Each service keeps its own copy of the allergen list | Rejected: the copies drift; one registry, read by id |
| Tags on listings only | Rejected: options carry their own allergens already, and seasonal options (a pumpkin spice shot) are a real case |
| Tags decide visibility by a `hidden` flag on the screen | Rejected: hiding in the UI leaks in the API and the cache; the catalog filters |

## Consequences

- **Easier:** one mechanism for the allergen list, dietary preference, holidays, themes and seasons; a closed allergen list that makes matching exact and the cart and order checks reliable; new tags are data, new filters and collections are reads of the same ids.
- **Harder:** the vendor API's contract changes (the allergen values become a closed list; `tags` appears); the seed data and any stored listings need migrating (local data only today); every public mapper must apply visibility and windows, and a test must show a hidden tag never appears.
- **Security and privacy:** a customer's allergens and preferences are quasi-health data (NFR 3.7) and live in the customer's own profile, not on the event backbone and not in tag data; hidden and platform tags cannot be set or read by a vendor through the public API; the registry endpoint exposes only public tags.
- **Observability:** tag ids are not personal data and may appear in logs and spans; a customer's profile never does.
- **Cost:** none new; the registry is a file, and a public cacheable response.

## Future uses (not decided; the design leaves room)

All of these are additions to the registry fields, the kinds or the readers, not a redesign.

- **Hidden tags for the platform:** ranking and boost signals, moderation flags ("needs review"), merchandising ("staff pick"), compliance labels (for example home-baker label requirements), sponsored eligibility, experiment cohorts, recommendation signals, analytics grouping.
- **Richer visibility:** recurring windows (breakfast hours, weekly specials) beyond a date range, region-bound visibility, visibility by customer segment.
- **Discovery:** collection and landing pages by tag, facet counts, per-tag search synonyms, tag groups and hierarchies (vegan implies vegetarian), translated labels.
- **Customers:** "prefer" on diet tags, interests on descriptive tags, notifications about a tag a customer follows.
- **Other subjects:** tags on vendors (badges), not only listings and options.
- **Governance:** administrator editing with an audit trail, tag merge and retirement, verification of claims.

## Plan if accepted

Work items, each tested before the next: **(1)** the registry, `GET /catalog/tags`, the closed allergen list validated on listings and options, and the seed migrated (this is the piece personalization needs); **(2)** `tags` on listings and options, vendor assignment through the API, visibility and windows applied in every public mapper, shown through the BFF and as chips on browse and detail; **(3)** filtering the public browse by tag; **(4)** diet tags in the customer's profile ("prefer") with a soft "not marked" signal, and the composition rule for options; **(5)** seasonal and themed surfaces, and administrator editing when the administrator service exists. Personalization (the allergen profile, the cart check and the allergens recorded on an order) depends on step 1 only. The data model document and the glossary gain the registry and the kinds with step 1.

## Amendment 2026-11-04 (acceptance)

The lead accepted this ADR and approved the nine allergens and their labels (the registry file `services/catalog-service/src/Tags/tags.json`) and the caps of 12 tags per listing and 6 per option. The lead's design rule for all of them: **they must be easy to adjust or extend.** In practice: the allergen list and its labels are data (a registry entry, not code), the web pages draw the allergen list from `GET /catalog/tags` and never name an allergen, and the caps are named constants or settings in one place (`TAG-002`), not numbers repeated in validators, tests and screens. Adding a tenth allergen is a registry change plus a matching listing-data change, not a code change.

## Amendment 2026-11-04 (the composition rule for a diet claim, WI-TAG-004)

Decided by the lead. A diet tag is the bakery's claim, and a configured item is **marked** for a diet only if the item carries the tag **and every chosen option carries it too**. An option with no tag therefore removes the claim; a vendor who forgets a tag produces "not marked", never a false claim (the rule fails safe). The cost, accepted, is that a vendor must tag every option of an item they mark, including neutral ones such as "Sliced". With no options chosen (browse, detail) a listing is marked when the item is, and the options that would remove the claim are named. "Not marked" is never worded as "not vegan", and no wording says an item is suitable, safe or free of anything. The rule lives in the catalog (`DietMatcher`); the BFF and the screens only show its answer. The alternatives considered and not taken: an explicit "breaks" marker on options (a forgotten marker gives a false claim) and a tag-or-neutral marker (a second marker and a heavier vendor model).
