# ADR-0024: Chaos Scenarios: Seeded, Configured Fault Injection at the Interface Layer

**Status:** Accepted (2026-11-11), after the seven scenarios ran on the whole local stack (see the note at the end). Proposed 2026-11-09: the lead decided the location, the scope (all services and the BFF) and that a new ADR is written. It extends ADR-0002 (chaos decorators and the Production gate) and ADR-0003 (events) and does not change either decision text; ADR-0002 is to be amended after this settles. The design and its assessment are in [chaos-scenarios-proposal.md](../chaos-scenarios-proposal.md).

## Context

ADR-0002 asked for a chaos decorator on the cache, and `ChaosEventTransport` (`WI-EVT-004`) followed the same pattern. Both exist only inside tests: nothing in a running service can switch them on, nothing records what they injected, and the draws of their random numbers depend on call order, so a run cannot be repeated under concurrency. Meanwhile the test tooling reaches faults by other routes: a control server that stops the BFF, headers that slow a response. Those routes add code and endpoints that exist only for tests (CLAUDE.md, register 150, 155).

The wish is one mechanism: faults introduced in a thin wrapper at an interface the system already has, chosen by a seed and configuration, with the service, the business logic and the external pieces untouched, usable against a running local or dev stack and not only in unit tests.

## Decision

1. **A scenario is data.** A named JSON document (name, seed, per-layer fault settings) in `chaos/scenarios/` at the repository root. It is selected by configuration (`Chaos:Enabled=true` and `Chaos:Scenario=<name or path>`), or passed as an object by an in-process test. The folder is shared by every language, so a scenario can cover a C# service and the Node BFF together. It is deliberately not inside a test project.
2. **Two small libraries read it:** `tools/BakeryMarketplace.Chaos` (C#: scenario loader, decision function, journal, `AddBakeryChaos`) and `packages/chaos` (TypeScript, same behaviour). `chaos/layers.json` is the shared list of layers and settings and `chaos/test-vectors.json` the shared expected numbers of the decision function; each library's tests check their copy against them, so the languages cannot drift. The existing `ChaosCacheProvider` and `ChaosEventTransport` move onto them without changing what they inject.
3. **Decisions are keyed, not drawn.** Whether a fault applies is a pure function of `(seed, layer, fault, operation key)`: the first 8 bytes of SHA-256 over those four joined by `|`, read as an unsigned big-endian integer, low 11 bits dropped and the rest divided by 2^53 (a value in [0, 1) exactly), compared with the fault's rate. The operation key is the event id, order id or request key the layer already has. The same scenario therefore hits the same operations on every run, under concurrency and in either language. A shared file of test vectors in `chaos/` is checked by both libraries' tests. Outage windows are measured from scenario start.
4. **Layers are interfaces that already exist.** A layer wraps the registered implementation and adds only faults: latency, errors, an outage window, rejection (a typed refusal such as a decline or a conflict), drop, duplicate, reorder, malformed input as far as the typed interface can express it, partial failure, and the **lost response**: the operation succeeds and the caller is told it timed out (every caller that retries must be idempotent, and this is how that is shown). Layers: `IEventPublisher`/`IEventSubscriber`, `ICacheProvider`, `IRepository<T>`, `IPaymentProcessor`, `INotificationSender`, `ICatalogGateway`, `IBroadcastPublisher`/`Subscriber` in the C# services; in the BFF a gate at the head of its HTTP handler (delay, reject with a chosen status, close the connection, never answer) and wrappers on its service clients. The web apps' server-side proxies may take the same gate. Every wrapper must pass the shared contract suite of its interface with chaos off. A scenario serves a whole stack, so a process applies the layers it has an interface for and reports the rest as not applicable (a layer name no process knows is rejected when the scenario is loaded). Wrappers for interfaces a service owns (payment, the catalog gateway, the notification sender) live in that service and are registered with `AddChaosLayer`, one line each.
5. **Wiring is in the composition root only.** One call, `AddBakeryChaos`, after a service's own registrations (and the equivalent in the BFF's `main.ts`), in catalog, ordering, notification and admin. No handler, domain class or resolver is edited. With no scenario it does nothing.
6. **Gating.** Chaos is refused at startup unless the host environment is Development or the setting `Deployment:Environment` is `dev`; UAT and Production refuse it (an allow-list, stricter than the deny-list of ADR-0002, which this does not weaken). The deployed dev stack's .NET services run as Development (a per-environment Terraform variable, `host_environment`, decided 2026-11-09; it ran as Production before), and its Terraform also sets `Deployment:Environment=dev`, which stays the setting that identifies the environment if the host name ever changes; only the dev environment's configuration may set it. The mock issuer stays Production in dev, deliberately, and does not run chaos. It also needs `Chaos:Enabled=true`. A startup warning names the scenario and seed and the health response says chaos is on. No deployment configuration outside the dev environment may name a chaos or deployment-environment setting, and a test (`scripts/ci/tests/chaos-not-deployed.test.mjs`) fails if one does.
7. **The response says so.** While a scenario is on, every HTTP response carries `X-Chaos-Scenario: <name>`, and `X-Chaos-Injected: layer:fault,...` lists the faults injected while that response was produced (GraphQL responses also carry `extensions.chaos`, with no schema change). It is response-only: no request header can switch chaos on or change it (as `X-Correlation-Id`, ADR-0016). It holds only the scenario name and layer and fault names, never ids, keys, payloads or the seed. Each process reports its own faults; the journals of several processes are joined by trace id, not by passing the indicator along.
8. **A journal records what happened.** Every injected fault is written as one structured log line and held in a `ChaosJournal` (layer, fault, operation key, time). A scenario run produces a summary of counts per fault, kept as evidence. There is no endpoint to read it. A scenario test asserts the journal shows the fault **before** it asserts the system coped.
9. **The cache layer sits under the fallback.** It wraps the *primary* store, so the result is `Resilient(Chaos(primary))` and the fallback is what gets exercised; wrapped around the resilient provider it would hide it. A service wires this where it builds the primary (one extra call there).
10. **The Node processes** have no host environment name, and their container image sets `NODE_ENV=production` everywhere, so the same gate reads `DEPLOYMENT_ENVIRONMENT` (`local` or `dev`; `NODE_ENV` of `development` or `test` also counts, an unset one does not) and the settings are `CHAOS_ENABLED` and `CHAOS_SCENARIO`. The BFF's layers are the gate at its door (before the body is read; `/healthz` is never disturbed) and wrappers on its two service clients that throw the same `DownstreamError` the real clients throw. At the door the decision key is the request's trace id when the caller sets its own `traceparent`, otherwise the request's number. A service's own faults are reported by that service; the BFF does not copy them to the client.
11. **What it does not touch.** Authentication, secrets and payment *integration* stay outside it as ADR-0005, 0006 and 0007 decided (the payment layer wraps the processor interface only, and the stub today). Stopping or restarting a process (the BFF's, the issuer's) and reading what a store holds stay process control and observation, not chaos.

## Consequences

- Where a stopped process is replaced by a gate at the BFF's door, the faults a client cannot tell apart from "unreachable" (reset, timeout, 5xx, non-JSON reply) are handled identically by the code that was read (the Android app's `gql` callers, the BFF's `callDownstream`, ordering's `DownstreamUnavailableException`); a test per call site must prove that before a flow stops using process control. "Connection refused" itself needs a stopped process.
- One mechanism replaces fault-only test paths below the BFF, with a seed, a record and no test-only endpoints. Process control and the data-read endpoints of the flow-control server remain (register 150).
- Each service gains one line of startup code and a dependency on the chaos library; business code is unchanged.
- A reproducible fault pattern is possible for the first time; timing (Redis redelivery, real clocks) is still not seedable, so scenario tests assert outcomes and counts, not durations.
- Malformed input is limited to what the typed envelope or request can express; corrupting bytes on the wire would need a proxy and is out of scope.
- The allow-list gate means a new environment name cannot run chaos until it is added on purpose.
- ADR-0002's wording (deny Production, decorators per library) becomes partly out of date; it is amended once this is accepted and has been run.

## Amendment 2026-11-10: aimed faults and signals (the lead approved both on 2026-11-10; local only, built and tested, not run on the whole stack)

The decision text above is unchanged. Two things are added to the scenario file, and the sentence "no request changes anything" is made precise.

1. **Aimed faults.** `failFirstAttempts` (a whole number, on `bffCatalog` and `bffOrdering`) fails the first N attempts of each operation and key, then lets the retry through; the existing keyed counters give the attempt number. A `where` section limits a layer to the calls that match: the client method (`operation`), the customer (`customer`, the `sub` of the bearer token), the call's key, and a `payload` pattern the call's first object or array argument must contain. A layer with no `where` disturbs every call, as before. A flow aims a fault by what it does (a particular order: the card, the listing and the quantity), not by a hook.
2. **Signals.** A scenario file may list `signals`: a normal request that matches a rule (the same match) makes the chaos runtime `enable` or `disable` a layer, `switch` to another scenario file of `chaos/scenarios/` (by plain name, never a path), or `reset` its counters and clock. A `off` list starts layers switched off so a signal can arm them. The request carries no setting, no layer and no scenario name: it only matches a rule the file already contains, so what can happen is fixed by the file the runner chose at startup. The matched request goes on as normal and is judged after the signal; every signal is in the journal. Signals work on calls through the BFF's two service clients; the C# processes check the sections (the same rules) and do not apply them, so one file is valid for the whole stack. A signal changes the state of the process that sees the request; changing another process's scenario needs a signal there.
3. **Identity.** The customer is read from the bearer token's payload without checking the signature, only to choose which calls a rule is about. It decides nothing about access; every service still validates the token itself (ADR-0006). The customer is not written to the journal or the logs.

The gate is unchanged: nothing here exists where chaos is refused, and a scenario without these sections behaves as before. `chaos/layers.json` lists the sections and the signal actions, and both libraries are tested against it.

## Acceptance note 2026-11-11

The lead accepted this ADR on 2026-11-11 on the condition that the evidence is documented. The decision text is unchanged. The evidence is in [`docs/evidence/WI-CHAOS-003/`](../../evidence/WI-CHAOS-003/README.md): seven scenarios (`checkout-trouble`, `lost-confirmation`, `flaky-broker`, `broker-outage`, `bff-door`, `web-door`, `slow-cache`) were each run on the whole local stack with every layer the scenario names, each journal showed the faults injected, and no run ended with a problem. The runs found two defects in the system that the unit tests had not (register 179 and 180 in checkout, 182 and 183 in the event outbox and redelivery, all fixed) and one gap that stays open (171, payment authorized twice and a notification sent twice, to be closed with a real provider). What the evidence does **not** cover, and so what this acceptance does not claim: (1) the aimed faults and signals of the amendment of 2026-11-10 on the Android emulator (flows 07 and 11 were never run; they are covered by unit and host tests only); (2) a failed cache invalidation leaving a stale entry until the TTL (`slow-cache` did not reach it); (3) the web servers keep no journal of the layers they applied, so `web-door` is shown by the browser's own figures. The Node allow-list (`DEPLOYMENT_ENVIRONMENT` local or dev, or `NODE_ENV` development or test) is accepted as built. ADR-0002 carries the matching amendment note.

Update the same day: limit (1) above is now covered: flows 07 and 11 ran on the emulator and passed under the BFF scenarios, and the BFF journal shows the signal, the aimed match and the one-shot failures (`docs/evidence/WI-CHAOS-003/flows-07-11-2026-11-11.md`; the `checkCart` rule and the `reset`, `enable` and `disable` signals were not exercised). The gap named above as open (171) was closed afterwards. The summaries of `lost-confirmation`, `flaky-broker` and `broker-outage` in the evidence folder were re-run on the final code, and so afterwards were the other four (`checkout-trouble`, `bff-door`, `web-door`, `slow-cache`): all seven passed with no problem and no known gap.
