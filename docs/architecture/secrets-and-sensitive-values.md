# Where secrets and private values live

> **Status:** Current · written 2026-11-20 for register item 214, at the lead's request; the lead decided the proposals the same day (the decisions are at the end, and in ADR-0020's note of 2026-11-20). Each row says how it is known: **seen** (checked on 2026-11-20), **schema** (the azurerm 4.81.0 provider schema), **design** (the code or an ADR, not run), **expected** (how the provider or platform behaves, not yet seen here). The dev environment has never been applied, so nothing about its state, vault or running apps is seen.

## What is protected

| Class | Examples | Rule |
|---|---|---|
| **Secret** (grants access) | Cosmos keys and connection strings, the ordering client secret, the session encryption key, the mock issuer's signing key, Log Analytics shared keys, access tokens and the pipeline's federated token | Never in the repository, never in a log or an artifact; held only where something must use it, for as short a time as the design allows (ADR-0007) |
| **Private value** (not a secret; this repository is public) | Subscription and tenant ids, principal object ids, the state account, registry, vault and Cosmos names, the budget e-mail | Never in the repository; allowed in pipeline variables, state, logs and local files that only the lead and the pipeline can read |
| **Configuration** | Ports, app names, regions, role names, secret *names* | Public |

## The boundaries

Persisted stores keep a value after the step that wrote it ends; transient ones lose it when the process, job or replica stops.

| Where | Kept | Who can read it | Holds | How known |
|---|---|---|---|---|
| **The repository** (public on GitHub) | Persisted, with full history | Everyone | Configuration only; examples use placeholders (`terraform.tfvars.example`, `backend.hcl.example`); the emulator's published fixed key | Seen: the gitleaks scan of the full history (626 commits, no leaks) and a search of this change for every private value |
| **The lead's machine** | Persisted on disk | The lead | Secrets: the local `.env` (local-only client secret, session key, mock signing key; `init-env.mjs`), the Azure CLI's token cache. Private values: `infra/foundation/backend.hcl` (git-ignored), the foundation variables file and saved plans in the agent's session scratchpad (cleared with the session), the agent's memory files | Design; seen for the files named |
| **Azure DevOps pipeline variables** | Persisted | Members of the private project who can edit the pipeline | Private values: subscription, state account, deploy principal, vault and Cosmos names. Plain variables, not secret ones | Design (set by the lead) |
| **Service connections** | Persisted | Project administrators | No secret: workload identity federation; each app registration has one federated credential and no password or certificate | Seen at the bootstrap (2026-11-19) |

| **Container Apps configuration** | Persisted | Readers of `rg-bakery-dev` | No value: each app secret is a Key Vault *reference*; the environment variables that are not secrets | Design |
| **A running replica** (environment and memory) | Transient (a restart or scale to zero ends it) | The process; anyone who can open a console in the app (Contributor on `rg-bakery-dev`: `bakery-deploy`, the lead) | Secrets: the platform resolves the references into environment variables at start (catalog and ordering: the Cosmos connection string; ordering: the client secret; web: the session key; the mock issuer: the client secret and a signing key it generates in memory, so tokens stop validating when it restarts) | Design; expected for the console |

## What the ADRs said, and what holds

- **ADR-0007:** "Terraform never writes literal secret values ... never committed to source control or visible in Terraform plan output", and sensitive variables are marked. **Holds**: the only value Terraform writes is the placeholder, which is not a secret, and the plan's text output masks the sensitive attributes. The rule is about where a value comes from and where it is shown.
- **ADR-0020 decision 4:** "State holds no secret values (ADR-0007)." **Holds for the foundation (seen), not for the dev stack** once it is applied: Terraform reads secrets back into state that it never wrote. The amendment of 2026-10-31 says "Secrets never pass through Terraform (decision 4, applied)" and describes the placeholder method, which supports the reading that the decision was about not authoring or copying secrets through Terraform and keeping them to the narrowest store, not about what a refresh records. That reading needs a dated note; it is the lead's to confirm.
- **ADR-0020 decision 5:** "The plan is published as an artifact." **Changed in practice** on 2026-11-20 (the lead's decision): the summary is published, the plan is not, because a plan holds the state's secrets in clear text. Needs a dated note.
- **Register 109:** "holds the account key as a Key Vault secret set after apply (never in state)". **Was not accurate**: with `value`, the key would have been in state twice (the account's attributes and the secret's read-back). With the write-only placeholder (decision 1) it is in state once, in the account's attributes; item 109 has a dated update.
- **The comment in `infra/environments/dev/main.tf`** ("Secrets whose real value never passes through Terraform or its state") had the same inaccuracy; it is corrected, and with decision 1 it is true for those three secrets.

## Against common practice

- HashiCorp's guidance is to treat every state file and every saved plan as sensitive: remote, encrypted at rest, access-controlled, and never published. Here the state is remote, Entra-only (no shared key), versioned and readable by three principals; saved plans are not published. **Met**; ADR-0020's note of 2026-11-20 says so instead of implying more.
- Prefer a **write-only** path for secrets a stack manages: Terraform 1.11 and later and azurerm 4.x offer `value_wo` and `value_wo_version` on `azurerm_key_vault_secret` (schema: present in 4.81.0), which are never stored in state or in a plan. **Used since 2026-11-20** (decision 1).
- Prefer **no secret** over a stored one (ADR-0007's own first rule): managed identity for Cosmos and local key authentication turned off makes the keys in state useless even when present. **Deferred** to after the first deploy (register 109; decision 2).
- Secrets in transit through a pipeline: never on a command line or in an echoed variable, masked in the log, written from a file in the job's temporary folder and deleted. **Decided before the step is built** (decision 3).
- Network as the only control (the Redis apps): common for internal-only dev components, but it means any compromised app in the environment can read the session store and the event stream. **Accepted for dev** (decision 5).

## Decisions (the lead, 2026-11-20)

1. **Done: the Key Vault placeholders are write-only** (`value_wo = "set-after-apply"`, `value_wo_version = 1` in place of `value` and `ignore_changes`), so the secrets' values never enter the dev state or a plan, even after the post-apply step. `required_version` of the dev stack is 1.11.0 (write-only attributes need it; the pipeline's 1.17.1 and the pull-request check image's 1.13.5 both meet it). The mocked tests check that the value is written only through `value_wo`, and a real plan's JSON no longer holds the placeholder. The version stays 1: raising it would overwrite the real values with the placeholder.
2. **Accepted: the Cosmos keys in the dev state** until register 109 (managed identity, after the first deploy) removes their use, with the state store's access control as the named control; and the **Log Analytics shared keys**, which the Container Apps environment sends its logs with.
3. **Decided: rules for the post-apply step**, before it is built: values never on a command line (`az keyvault secret set --file` from a file created with mode 600 in the job's temporary folder, then deleted), masked with `##vso[task.setsecret]`, no shell tracing, only in the approved stage on `main`. The pipeline structure tests hold the first and the third.
4. **Done: dated notes** with the decision text unchanged: ADR-0020's note of 2026-11-20 (decisions 4 and 5, and the step's rules), an update to register 109, the comment in `infra/environments/dev/main.tf`.
5. **Accepted for dev: the Redis apps' network boundary** (no password, internal ingress). A password from Key Vault, like the other secrets, comes before any use beyond the demo environment.
6. **No action: earlier state versions.** Versions written before 1 would still hold old values until soft delete and versioning age them out (30 days); none exist for the dev stack, which has never been applied. After a teardown the Cosmos keys in old versions open nothing, since the account is gone.
